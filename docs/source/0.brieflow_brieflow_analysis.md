# Brieflow and Brieflow Analysis

## Overview

A screen analysis uses two repositories that are built together:

- [brieflow](https://github.com/cheeseman-lab/brieflow): the pipeline code that processes OPS data at scale.
- [brieflow-analysis](https://github.com/cheeseman-lab/brieflow-analysis): a template for one screen, holding the notebooks that set parameters, the {term}`screen.yaml` description, the {term}`config.yml` they write, and `flow.sh`, which runs the pipeline.

Each screen gets its own copy of brieflow-analysis, with brieflow pinned inside it as a git submodule.

```{note}

The `marimo` branch holds the marimo notebooks (`analysis/0_preprocess.py` … `analysis/12_analyze.py`) and pins the brieflow line with OME-Zarr support; these docs describe it.
The `main` branch holds the older Jupyter notebooks; see [Moving from the Jupyter Notebooks](migrating_from_jupyter.md).
```

## Brieflow

### Components

Brieflow follows the [Snakemake structure guidelines](https://snakemake.readthedocs.io/en/stable/snakefiles/deployment.html), with a few exceptions:

```
workflow/
├── lib/       library code that does the processing, organized by module plus shared and external code
├── scripts/   one Python script per rule; loads inputs, calls lib, saves outputs
├── rules/     Snakemake rules per module: inputs, outputs, params and the script to run
├── targets/   the output files each module produces, and their wildcards
└── Snakefile  loads the config and includes each module's targets and rules
```

A run flows top-down:

- A notebook in brieflow-analysis sets parameters and writes them to `config/config.yml`.
- `flow.sh` runs the main `Snakefile` with that config, locally or on Slurm.
- The `Snakefile` includes the targets and rules of every configured module.
- Each rule calls a script, and each script calls library code to turn the rule's inputs into its outputs.

### Example: calling reads

Read calling in the SBS module shows each layer.

1. The main [Snakefile](https://github.com/cheeseman-lab/brieflow/blob/main/workflow/Snakefile) includes the SBS targets whenever the config has an `sbs` section, and the SBS rules unless `flow.sh` switched them off:

   ```python
   if "sbs" in config:
       include: "targets/sbs.smk"
   if _bool_cfg("sbs_rules_enabled") and config.get("sbs", {}).get("enabled", True) and "sbs" in config and len(sbs_wildcard_combos) > 0:
       include: "rules/sbs.smk"
   ```

2. The [targets](https://github.com/cheeseman-lab/brieflow/blob/main/workflow/targets/sbs.smk) name the read-calling output. `get_data_output_path` gives a flat filename in TIFF mode and a nested `plate/row/col/tile` path in zarr mode:

   ```python
   "call_reads": [
       SBS_FP / "tsvs" / get_data_output_path(_tile, "reads", "tsv", SBS_IMG_FMT),
   ],
   ```

3. The [rule](https://github.com/cheeseman-lab/brieflow/blob/main/workflow/rules/sbs.smk) says how to make it, and reads its parameters from the config:

   ```python
   rule call_reads:
       input:
           SBS_OUTPUTS["extract_bases"],
           SBS_OUTPUTS["find_peaks"],
       output:
           SBS_OUTPUTS_MAPPED["call_reads"],
       params:
           chemistry=config.get("sbs", {}).get("chemistry", "four_color"),
           call_reads_method=config.get("sbs", {}).get("call_reads_method", "median"),
           combinatorial=config.get("sbs", {}).get("combinatorial", None),
           codebook_fp=config.get("sbs", {}).get("df_barcode_library_fp", None),
           error_correct=config.get("sbs", {}).get("error_correct", False),
       script:
           "../scripts/sbs/call_reads.py"
   ```

4. The [script](https://github.com/cheeseman-lab/brieflow/blob/main/workflow/scripts/sbs/call_reads.py) loads the inputs, calls the library and saves the output:

   ```python
   bases_data = pd.read_csv(snakemake.input[0], sep="\t")
   peaks_data = read_image(snakemake.input[1])

   reads_data = call_reads(
       bases_data=bases_data,
       peaks_data=peaks_data,
       method=snakemake.params.call_reads_method,
       chemistry=snakemake.params.chemistry,
       combinatorial=snakemake.params.combinatorial,
       codebook=codebook,
   )
   reads_data.to_csv(snakemake.output[0], index=False, sep="\t")
   ```

5. The [library function](https://github.com/cheeseman-lab/brieflow/blob/main/workflow/lib/sbs/call_reads.py) does the work:

   ```python
   def call_reads(
       bases_data,
       peaks_data=None,
       correction_only_in_cells=True,
       normalize_bases_first=True,
       method="median",
       chemistry="four_color",
       combinatorial=None,
       codebook=None,
   ):
   ```

## Brieflow Analysis

The analysis repository holds everything that is specific to one screen.
For the read-calling example above:

1. Open the SBS notebook, `analysis/2_sbs.py`, in marimo (see [Working with the Notebooks](notebook_editor_setup.md)).
2. Set `CALL_READS_METHOD` in its {term}`operator parameter <Marker block>` cell:

   ```python
   # === OPERATOR PARAMETERS ===
   THRESHOLD_READS = 50  # library default; raise to be stricter
   CHEMISTRY = "four_color"  # "four_color" | "combinatorial"
   # four_color: median|percentile; combinatorial: frac|merfish
   CALL_READS_METHOD = "median"
   ...
   # === END OPERATOR PARAMETERS ===
   ```

3. The notebook's last cell adds an `sbs` section to the config and rewrites `config/config.yml`:

   ```python
   config["sbs"] = {
       ...
       "chemistry": CHEMISTRY,
       "call_reads_method": CALL_READS_METHOD,
       ...
   }
   ```

4. `bash flow.sh sbs` runs the SBS module, and the rule passes `call_reads_method` to the script as shown above.

## Reproducibility and modularity

Keeping the two repositories apart lets you:

- change one process (for example `call_reads`) without touching the rest;
- use one brieflow branch across several screen repositories;
- see exactly how a screen's brieflow differs from `main`, since the submodule pins a commit;
- publish a whole screen analysis on GitHub.
