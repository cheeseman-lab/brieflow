# Running a Screen

## Overview

Each large brieflow process is a *module*: preprocess, SBS, phenotype, merge, aggregate, cluster and mozzarellm.
Every module has a marimo notebook in brieflow-analysis that sets its parameters, and targets and rules in brieflow that run it.
Classify has a notebook but no module of its own; aggregate applies the classifier it trains.

The loop for each phase is the same:

1. **Configure**: open the phase's notebook, set its parameters against a test tile or well, and let its last cell write the phase's section of `config/config.yml` (see [How a notebook reaches config.yml](notebook_editor_setup.md#how-a-notebook-reaches-configyml)).
2. **Dry run**: `bash flow.sh <module> --dry-run` shows the jobs Snakemake would run.
3. **Run**: `bash flow.sh <module>` locally, or with `--backend slurm` on a cluster.
4. **Check**: review the phase's `eval/` plots and tables (or the [visualizer](4.visualization.md)) before configuring the next phase, since later notebooks load this phase's outputs.

Work from the `analysis/` directory with the screen's environment active:

```bash
cd analysis/
conda activate brieflow_SCREEN_NAME
```

## Notebooks and modules

The numbers in the notebook names are historical and have gaps; the table gives the order to run them in.

| Order | Notebook | Config section | Run with | Key outputs (under `brieflow_output/`) |
|---|---|---|---|---|
| 1 | `0_preprocess.py` | `all`, `preprocess` | `bash flow.sh preprocess` | `preprocess/`: per-tile images, metadata tables, IC fields |
| 2 | `2_sbs.py` | `sbs` | `bash flow.sh sbs` | `sbs/`: reads, cells and per-cell barcode calls; mapping QC in `sbs/eval/` |
| 3 | `3_phenotype.py` | `phenotype` | `bash flow.sh phenotype` | `phenotype/`: aligned images, masks, per-cell features |
| 4 | `5_merge.py` | `merge` | `bash flow.sh merge` | `merge/parquets/`: one `merge_final` table per well |
| 5 | `7_classify.py` (optional) | `classify` | applied by `aggregate` | a trained classifier file |
| 6 | `8_aggregate.py` | `aggregate` | `bash flow.sh aggregate` | `aggregate/`: filtered cells, aligned embeddings, per-perturbation profiles, bootstrap results, montages |
| 7 | `10_cluster.py` | `cluster` | `bash flow.sh cluster` | `cluster/`: PHATE/Leiden clusters and benchmarks per resolution, and a `cluster.h5ad` |
| 8 | `12_analyze.py` | `mozzarellm` | `bash flow.sh mozzarellm` (optional) | plots in the notebook; LLM annotations under each annotated resolution |
| 9 | — | — | `bash flow.sh viz` | the Streamlit visualizer |

SBS and phenotype are independent, so their notebooks can be configured in either order and the two modules run together with `bash flow.sh sbs phenotype`.

## flow.sh

`flow.sh` runs one or more modules by name, in the order given:

```bash
bash flow.sh <module> [module2 ...] [options]
```

| Module | Runs |
|---|---|
| `preprocess`, `sbs`, `phenotype`, `merge`, `aggregate`, `cluster`, `mozzarellm` | Snakemake up to that module's `all_<module>` target |
| `all` | `preprocess sbs phenotype merge aggregate cluster` in order (not `mozzarellm`) |
| `viz` | the Streamlit visualizer on `brieflow_output/` (see [Visualization](4.visualization.md)) |

The rules of every module you did not name are switched off for the run, so running `aggregate` never re-runs SBS or phenotype jobs; if an upstream output is missing, run that module explicitly.

| Option | Effect |
|---|---|
| `--backend local\|slurm` | Run jobs on this machine (default) or submit them to Slurm |
| `--dry-run`, `-n` | Show what would run without running it |
| `--cores N` | Cores for the local backend (default: all) |
| `--jobs N` | Maximum concurrent jobs (default: the Slurm profile's `jobs:`, or `--cores` locally) |
| `--sequential-plates`, `--plates N` | Run preprocess, SBS and phenotype one plate at a time. This is already the default for those three modules; the plate count is read from the sample tables unless `--plates` gives it |
| `--only-plate N` | Run preprocess, SBS or phenotype for plate `N` only |
| `--arrays` | Submit Slurm array jobs (off by default, see below) |
| `--profile` | Keep all Slurm logs and write a Slurm efficiency report to `logs/` |
| `--forcerun rule1,rule2` | Re-run the named rules even if their outputs are up to date, for example after editing a rule's script |
| `--unlock` | Remove a stale Snakemake lock first (`flow.sh` also does this automatically when it finds one) |
| `--slurm-profile DIR` | Use a different Slurm profile directory (default: `slurm/`) |
| `--help`, `-h` | Print the full usage |

Every run is logged to `analysis/logs/<modules>-<timestamp>.log`.
Snakemake is called with `--rerun-triggers mtime` and `--rerun-incomplete`, so a job killed mid-write (an out-of-memory kill, a lost node) is re-run on the next invocation.

On the local backend, `flow.sh` gives Snakemake a memory budget of 90% of the machine's RAM, so per-rule memory limits throttle how many heavy jobs run at once; set `BRIEFLOW_LOCAL_MEM_MB` to change the budget.

## Running on Slurm

```bash
tmux new-session -s my_screen
bash flow.sh sbs phenotype --backend slurm
```

- Snakemake runs where you start `flow.sh` (usually the login node) and submits each job to Slurm, so start it inside `tmux` or `screen`.
- Jobs take their resources from `analysis/slurm/config.yaml`: set `slurm_partition` and `slurm_account` under `default-resources` for your cluster, and adjust per-rule `mem_mb`/`cpus_per_task` under `set-resources` if a rule runs out of memory. `jobs:` caps concurrent jobs.
- Per-tile SBS and phenotype rules are grouped, so one Slurm job processes all steps of a tile.
- Job logs go to `analysis/slurm/slurm_output/rule/`.
- Slurm array jobs are **off by default**: with `snakemake-executor-plugin-slurm` 2.6.0, the version brieflow pins, every array task after the first is reported as failed and its outputs deleted. `--arrays` turns them on if your executor version handles them.
- If the [brieflow-auto](brieflow_auto.md) plugin is installed, `flow.sh` finds its resource resolver and passes per-rule memory caps to Snakemake; set `BRIEFLOW_SKIP_RESOLVE=1` to use only the profile.

Other Snakemake executors are listed in the [Snakemake plugin catalog](https://snakemake.github.io/snakemake-plugin-catalog/index.html); only Slurm has been tested.

## Output formats: TIFF and zarr

The preprocess notebook's `IMAGE_FORMAT` (`all.image_format` in the config) picks how outputs are stored, for the whole run:

| | `tiff` | `zarr` (the notebook default) |
|---|---|---|
| Images | one file per tile and image type, for example `sbs/images/P-1_W-A1_T-0__aligned.tiff` | one {term}`OME-Zarr` plate store per image type, with wells and tiles as groups, for example `phenotype/aligned_1.zarr/A/1/2/`; masks are stored as labels inside the image store |
| Per-tile tables | flat file names, for example `sbs/tsvs/P-1_W-A1_T-0__reads.tsv` | nested directories, for example `sbs/tsvs/1/A/1/0/reads.tsv` |
| Well and screen tables | flat file names in both modes, for example `merge/parquets/P-1_W-A1__merge_final.parquet` | |

Zarr stores open directly in OME-Zarr viewers such as napari.
The pipeline parameters are the same in both modes; the small test runs both.

Clustering outputs have the same layout in both modes: one directory per {term}`channel combo <Channel combo>`, optional {term}`compartment combo <Compartment combo>`, {term}`cell class <Cell class>` and Leiden resolution:

```
cluster/
└── DAPI_COXIV_CENPA_WGA/            channel combo
    └── cell-nucleus-cytoplasm/      compartment combo (only when SPLIT_BY_COMPARTMENT is on)
        └── Interphase/              cell class
            ├── aggregate_cleaned.tsv
            ├── h5ad/cluster.h5ad    every resolution in one AnnData file
            └── 2/                   Leiden resolution
                ├── phate_leiden_clustering.tsv
                ├── clusters.png
                └── CB-Real__global_metrics.json …
```

## Module by module

### Preprocess

**Configure**: `0_preprocess.py`.
Point `SBS_IMAGES_DIR_FP` and `PHENOTYPE_IMAGES_DIR_FP` at the raw data, give a regular expression that extracts plate, well and tile (and cycle, for SBS) from each path, and choose `IMAGE_FORMAT` and the output root `ROOT_FP` (default `brieflow_output/`).
The notebook writes the sample and combo tables under `config/`, test-converts one file of each kind, and writes the `all` and `preprocess` config sections.

- Inputs can be ND2, Imaris (`.ims`) or TIFF, with one tile per file or a whole well per file. A single-position ND2 well file is read as one tile.
- Leave one image directory as `None` to configure only SBS or only phenotype; its sample table is then empty and the pipeline skips that arm's rules.
- `SAMPLE_FRACTION` below 1 computes each {term}`IC field` from a random subset of tiles. The subset is drawn with a fixed seed, so reruns give the same field.

**Run**: `bash flow.sh preprocess` (add `--backend slurm` on a cluster).

### SBS

**Configure**: `2_sbs.py`.
Name the channels, choose cycle alignment and spot detection, pick a segmentation method (Cellpose, StarDist or watershed), point `DF_DESIGN_FP` at the barcode library, and tune read calling on a test tile: `CHEMISTRY` (`four_color` or `combinatorial`), `CALL_READS_METHOD`, `THRESHOLD_READS` and `Q_MIN`.
The notebook plots {term}`mapping rate` against the read threshold to guide the choice.

**Run**: `bash flow.sh sbs`, or together with phenotype: `bash flow.sh sbs phenotype`.

### Phenotype

**Configure**: `3_phenotype.py`.
Name the channels, align them if they were not captured consecutively, segment nuclei and cells, and choose feature extraction (`CP_METHOD`: the default `cp_emulator`, or `cp_measure`).

- **GPU.** `GPU` controls the notebook's own test segmentations; `PIPELINE_GPU` is what the pipeline's `segment_phenotype` and `identify_second_objs` jobs use (`phenotype.gpu`). Leaving `PIPELINE_GPU = None` uses `GPU`, so you can tune on a GPU node and still segment on CPU by setting `PIPELINE_GPU = False`, or the reverse. On Slurm, a GPU job also needs a GPU partition and a GPU request in the profile.
- **Secondary objects** (optional). Set `SECOND_OBJ_DETECTION = True` and `SECOND_OBJ_CHANNEL` to segment objects inside cells, such as an intracellular pathogen, organelles or foci, with a threshold, Cellpose or StarDist method. Each object is measured and assigned to its cell; `8_aggregate.py` decides how per-object features enter the cell profile (`SECOND_OBJ_AGG_STRATEGY`), and cell-level columns such as `has_second_obj` and `num_second_objs` are available to filters.
- **Custom features.** `CUSTOM_FEATURES` adds your own per-cell measurements to `cp_emulator` output.

**Run**: `bash flow.sh phenotype`.

### Merge

**Configure**: `5_merge.py`.
Merge matches each phenotype cell to its SBS cell.
The default `fast` approach aligns tiles by hashing triangles of nuclear centroids: it needs a handful of initial phenotype-tile/SBS-tile pairs (`INITIAL_SITES`, or `INITIAL_SBS_TILES` to find them from stage coordinates), a valid magnification ratio (`DET_RANGE`) and a match distance (`THRESHOLD`).
An optional `stitch` approach stitches whole wells instead, and advanced levers for difficult alignments are available and written only when set.
The RANSAC fit that refines each tile alignment uses a fixed seed, so merges are reproducible; there is no seed setting.

**Run**: `bash flow.sh merge`.

### Classify (optional)

**Configure**: `7_classify.py`.
Label example cells interactively, train and compare classifiers, and save the chosen one.
The notebook writes a `classify` section (classifier path, class mapping, confidence thresholds); `aggregate` applies it to split cells into classes.
Without a classifier every cell is in one class, `all`.

### Aggregate

**Configure**: `8_aggregate.py`.
Aggregate turns merged single cells into one profile per perturbation for each cell class and channel combo: filter cells, drop and impute missing values, score perturbation strength, normalize with {term}`TVN`, and aggregate by median or mean.
Optional bootstrap scoring tests each perturbation's features against a control null.

- **Per-well annotations.** `WELL_ANNOTATIONS_FP` names a TSV with columns `plate`, `well` and one column per experimental variable (for example `treatment`). The annotations are joined onto every cell, and only annotated wells are aggregated, so leaving a well out of the table excludes it.
- **Splitting.** `SPLIT_COL` decides which cells form separate datasets, each with its own embedding. The default `"class"` splits by the classifier; naming an annotation column instead splits by its values (for example one dataset per treatment), read from the annotation table. An `all` dataset is always made as well.
- **Grouping.** `GROUP_COLS` aggregates within annotation groups instead, so a profile is perturbation × group in one shared embedding.
- **Controls.** `CONTROL_KEY` names the control perturbation (for example `nontargeting`); `CONTROL_NAME_COL` lets controls be recognized from a different column.
- **Batch correction.** With `TVN_BATCH_CORRECTION = True` (the default) TVN is fit on each batch's own control cells; set it to `False` to fit once on pooled controls when batches hold few controls, or when only some batches contain the control.
- **Bootstrap {term}`control scope <Control scope>`.** `BOOTSTRAP_CONTROL_SCOPE` picks the null: `pooled` (all controls), `within_group` (controls in the same group), `reference_group` (controls in `BOOTSTRAP_REFERENCE_GROUP`), or `within_perturbation` (the perturbation's own arm in the reference group, for perturbations that are not knockouts, scored against their vehicle arm).
- **Compartments.** `SPLIT_BY_COMPARTMENT` with `COMPARTMENT_COMBOS` aggregates separately for sets of compartments (cell, nucleus, cytoplasm, secondary objects).

**Run**: `bash flow.sh aggregate`.

### Cluster

**Configure**: `10_cluster.py`.
Choose minimum cells per perturbation, the PHATE distance metric, an optional perturbation AUC filter, and test Leiden resolutions against the benchmarks; list the resolutions to run in `FINAL_LEIDEN_RESOLUTIONS`.
`SPECIES_ID` selects the organism for the CORUM, KEGG and STRING {term}`benchmarks <Benchmarks>`.

- `CONTROL_SCOPE` and `CONTROL_REFERENCE_GROUP` pick the controls each point's distance to controls is averaged over, with the same four scopes as the bootstrap. They only matter when `GROUP_COLS` was set in aggregate.
- `CLUSTER_CONTROL_KEY` (`cluster.control_key`) overrides the aggregate `CONTROL_KEY` for clustering, for example when the aggregate key names a treatment through `CONTROL_NAME_COL` but the cluster-space null needs control perturbations.

**Run**: `bash flow.sh cluster`.

### Analyze

`12_analyze.py` reports pipeline statistics, ranks resolutions by a benchmark metric to suggest an optimal one, and draws feature, volcano and montage plots for a chosen clustering.
The clustering you pick (`CHANNEL_COMBO`, `CELL_CLASS`, `LEIDEN_RESOLUTION`) is saved in the `mozzarellm` config section and is also where the visualizer opens.

### MozzareLLM

LLM-based cluster annotation with [MozzareLLM](https://github.com/cheeseman-lab/mozzarellm), run as a pipeline module over a chosen subset of the clusterings.

**Prerequisites**: the `mozzarellm` extra (see [Installation](2.installation_analysis_setup.md)) and the model provider's API key in `analysis/.env`, for example `ANTHROPIC_API_KEY=...`; `flow.sh mozzarellm` exports it to the jobs.

**Configure**: the MozzareLLM cells at the end of `12_analyze.py`.
They write one screen-context JSON per selected clustering into `config/mozzarellm_context/`, the combo table `config/mozzarellm_combo.tsv`, and the `mozzarellm` config section, and end with a dry run that prices the selection before any model is called.
Each context is derived once from `screen.yaml` and `config.yml` and then belongs to you: an existing context file is never overwritten unless `MOZZARELLM_REWRITE_CONTEXTS = True`.
A channel's `description` in `screen.yaml` is inherited by every context that contains it.

The section the notebook writes looks like this:

```yaml
mozzarellm:
  cell_class: Interphase
  channel_combo: DAPI_COXIV_CENPA_WGA
  leiden_resolution: 2
  combo_fp: config/mozzarellm_combo.tsv
  run_name: run1
  screen_name: my_screen
  model: claude-sonnet-5
  mode: cot
  mcp: true
  source: affinage_then_uniprot
  include_features: auto
  include_strength: auto
  n_features: 20
  fdr_threshold: null
  max_tokens: 64000
  max_workers: 8
  max_failed_clusters: 2
  runtime: 720
```

`screen_name` comes from `experiment.screen_title` in `screen.yaml` and prefixes every output file.

`source` picks the functional annotation the evidence bundles carry: `affinage_then_uniprot` (the default), `affinage` (MozzareLLM's benchmark-selected source), `uniprot`, or `both`. The three pure sources backfill nothing, so a gene one source has nothing for reaches the model as a visible gap.

`affinage_then_uniprot` is the production default because that gap is costly here: MozzareLLM's `DARK_GENE` subclass means a gene identified only by a raw identifier with no annotation of any kind, so a gene Affinage lacks but UniProt describes well would arrive blank and be eligible to be called a dark gene. It fetches Affinage for every gene, then queries UniProt **only** for the genes whose Affinage annotation is absent, empty, or a refusal narrative — so request volume and prompt length stay close to pure `affinage`, unlike `both`, which carries two annotations for every gene. Each gene in the bundle carries an `annotation_source` field (`affinage`, `uniprot`, or empty when neither source had anything), so a mixed run stays auditable per gene and a curated UniProt FUNCTION line is never mistaken for an Affinage narrative. A gene neither source has still arrives blank; the fallback narrows the gap rather than inventing one.

Stable accessions always come from UniProt whatever the source, since they are UniProt identifiers.

`mozzarellm_combo.tsv` holds one row per clustering to annotate, with columns `cell_class`, `channel_combo`, `leiden_resolution`, `screen_context_fp` and, for compartment-split runs, `compartment_combo`. It is deliberately a subset of `cluster_combo.tsv`.

**Run**: `bash flow.sh mozzarellm --backend slurm` submits one job per row of the combo table.

`rule annotate_clusters` writes `mozzarellm/<run_name>/<screen_name>_clusters.json` and `_genes.csv` beside the clustering, resuming from the run's traces if a job is retried. `rule annotate_cluster_anndata` merges those calls back into `cluster_annotated.h5ad`, the single artifact the visualizer and downstream analysis read.

### Visualization

```bash
bash flow.sh viz
```

starts the Streamlit visualizer on `brieflow_output/` with `config/config.yml` and `screen.yaml`; see [Visualization](4.visualization.md).

## Reproducibility

- Every random step with no scientific choice behind it is seeded at 0 in code: the tile subset for illumination correction and the RANSAC fit in merge. There are no seed settings; a `merge.ransac_random_state` key left in an older config is ignored.
- `config/config.yml`, the sample and combo tables, and the brieflow submodule commit together describe a run; commit them with the screen repository.
